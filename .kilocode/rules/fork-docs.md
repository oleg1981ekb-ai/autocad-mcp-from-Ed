# Правила работы в форке (fork-docs)

При работе над проектом внутри форка (`docs/fork/`), как при задачах по портированию
на macOS или внесению архитектурных изменений, следуй этим правилам:

1. Любое архитектурное решение, связанное с портом, миграцией или изменениями
   контракта/протокола/инструментов, фиксируй в новом файле
   `docs/fork/ADR/NNNN-<slug>.md` по шаблону (Статус, Контекст, Решение, Последствия)
   и ссылаться на него из `docs/fork/TODO.md`.

2. После завершения каждого этапа или готовности шага портирования обновляй
   `docs/fork/TODO.md`: помечай задачи `[x]` / `[~]`, добавляй новые с
   приоритетами.

3. При любом значимом изменении в коде, конфигурации, процессах сборки или
   документации, которое относится к форку, добавляй запись в
   `docs/fork/CHANGELOG_FORK.md` в формате Keep a Changelog: `Added`,
   `Changed`, `Fixed`, `Removed`, `Security` (если применимо) — с версией
   или `Unreleased`.

4. Не редактируй `CHANGELOG.md` (главный апстрим-ченжлог) и `docs/PROJECT_GUIDE.md`
   без явной задачи пользователя; правки проекта вне форка — вне этой схемы.

5. Все правки документации флага делай только после подтверждения пользователя —
   не начинай архитектурные изменения без согласования.
