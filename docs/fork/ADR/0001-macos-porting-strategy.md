# ADR-0001: Стратегия портирования на macOS (AutoCAD 2027)

- **Статус:** Принято
- **Дата:** 2026-11-13
- **Контекст:** см. раздел ниже
- **Решение:** см. раздел ниже
- **Последствия:** см. раздел ниже

## Контекст

`Nodal.AcadMcp` — MCP-сервер для AutoCAD 2027 (R26.0) и AutoCAD Architecture,
написанный на C# под .NET 10. Сегодня он жёстко привязан к Windows:

- Адд-ин `Nodal.AcadMcp.Addin` нацелен на `net10.0-windows` и использует WPF
  (`UseWPF=true`) для окна статуса и ленты.
- Ссылки на AutoCAD.NET (`AutoCAD.NET` 26.0.0), ACA (`AecBaseMgd.dll` и др.) и
  Roslyn берутся из установки AutoCAD по путям Windows
  (`C:\Program Files\Autodesk\AutoCAD 2027`), см. `Directory.Build.props`.
- Развёртывание выполняет `deploy.ps1` (PowerShell), раскладывая бандл в
  `%APPDATA%\Autodesk\ApplicationPlugins` и `%LOCALAPPDATA%\Nodal.AcadMcp`.
- Ядро (`Nodal.AcadMcp.Contracts`, `Nodal.AcadMcp.Server`) уже платформенно-
  нейтрально: `net10.0`, без ссылок на AutoCAD и без WPF. Тесты также не
  зависят от AutoCAD.

Задача — получить сборку и запуск на macOS под AutoCAD 2027, **не сломав**
текущую сборку и поведение на Windows. Обратная совместимость с Windows —
обязательное требование: существующий `deploy.ps1`, бандл и все 159
инструментов должны продолжать работать без изменений для пользователей
Windows.

Ключевое техническое ограничение: платформенная часть (WPF-UI и доступ к
установленным сборкам AutoCAD) не переносится на macOS напрямую, а
AutoCAD для macOS предоставляет иной набор API/расширений, чем Windows.
Поэтому «портирование» — это не смена одной строки TargetFramework, а
разделение платформенно-нейтрального ядра и платформенных оболочек.

## Решение

Принять стратегию **«общее ядро + платформенные оболочки»**:

1. **Оставить ядро кроссплатформенным.** `Nodal.AcadMcp.Contracts` и
   `Nodal.AcadMcp.Server` остаются на `net10.0` без платформенных
   зависимостей и собираются/тестируются на macOS и Windows одинаково.
   Вся бизнес-логика, протокол (`AcadMcpProtocol`), схемы, guard-правила и
   MCP-прокси живут здесь.

2. **Изолировать Windows-специфичный UI.** WPF (окно статуса, лента)
   выносится в отдельную Windows-only часть за условной компиляцией.
   На macOS WPF не используется; функциональность, зависящая от UI,
   либо заменяется платформенной реализацией, либо отключается, не затрагивая
   мост и инструменты.

3. **Ввести условную компиляцию через TargetFramework.** Адд-ин получает
   многоплатформенную цель (`net10.0-windows` для Windows и macOS-ветку),
   платформенные участки закрываются символами (`WINDOWS`, `MACOS`) и
   условиями MSBuild. Ссылки на сборки AutoCAD берутся из
   платформенно-зависимых путей, а Windows-пути остаются значением по
   умолчанию.

4. **Добавить macOS-скрипт развёртывания** (`deploy.sh`) по образцу
   `deploy.ps1`, не изменяя поведение последнего. Windows-пользователи
   продолжают пользоваться `deploy.ps1`.

5. **Проверять на живом AutoCAD 2027** на обеих платформах: Windows — как
   регрессия существующего поведения, macOS — как приёмка порта. Тесты без
   AutoCAD (`dotnet test`) обязательны на обеих платформах.

## Последствия

**Положительные:**
- Обратная совместимость с Windows сохраняется: `deploy.ps1`, бандл и
  инструменты не меняются для существующих пользователей.
- Ядро и тесты становятся по-настоящему переносимыми; CI может гонять
  `dotnet test` на macOS и Windows без AutoCAD.
- Платформенные различия локализованы в оболочках, а не размазаны по коду.

**Отрицательные / риски:**
- Усложняется сборка: появляется условная компиляция, платформенные цели
  и два скрипта развёртывания — растёт стоимость поддержки.
- Платформенные различия AutoCAD (API/расширения на macOS) могут потребовать
  отдельных реализаций моста или части инструментов; объём этой работы на
  старте неизвестен и уточняется на этапе разведки.
- Часть Windows-only функциональности (WPF-окно, лента) на macOS может быть
  недоступна или реализована иначе — это нужно явно документировать.

**Обязательства:**
- Каждое архитектурное изменение в рамках порта фиксируется новым ADR.
- Пошаговый план ведётся в `docs/fork/TODO.md`, история изменений — в
  `docs/fork/CHANGELOG_FORK.md`.

## Альтернативы

- **Полный форк под macOS без общей кодовой базы.** Отклонено: дублирование
  протокола, схем и инструментов, риск расхождения поведения и потеря
  обратной совместимости с Windows.
- **Отказ от WPF и переход на кроссплатформенный UI сразу для обеих ОС.**
  Отклонено на этом этапе: слишком большой объём изменений и риск регрессии
  для Windows; UI изолируется, а не переписывается целиком.
